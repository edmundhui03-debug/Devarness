# Task support

Use this optional style for the requested task. A request to use it for the
whole session persists until the user says to stop. Do not infer any medical
condition or reading ability. This adapts the practical output habits of
[i-have-adhd](https://github.com/ayghri/i-have-adhd/tree/24d22f783e57cb73c957848b588c6f651b6f9cd8),
copyright 2026 Ayoub Ghriss, under the accompanying [MIT license](LICENSE).

The user's instructions and the dev router govern. Superpowers owns planning,
debugging and verification gates; this skill only makes their results easier to
act on. It does not add approval requests, task tracking systems or hooks.

## Keep the current action clear

Lead with the result, finding, or action that matters now. For work the user
must perform, use a short numbered list with one bounded action per step. Prefer
a few immediate actions; preserve the full task scope in its existing plan or
task card. Do authorized work yourself when the tools support it.

When returning after an interruption, identify the current objective and the
last verified result before continuing. During longer work, update the existing
checklist as results arrive. Use its native statuses; do not duplicate the plan
or impose a new sequence on independent parallel work.

Keep progress factual: a file created, a command that passed, or a specific
behavior reproduced. Distinguish completed work from planned, deferred, blocked
and unverified work. A check passing on one platform does not establish another
platform's acceptance. Never invent progress percentages, runtimes, costs or
verification. Give estimates only when useful, with units and assumptions.

Answer questions that arrive during work, then continue the active objective.
Keep incidental observations in the existing record when they matter; do not
turn them into extra decisions for the user. State errors with the failing
operation and available evidence. Preserve uncertainty when the cause is
unknown.

## Leave a usable reentry note

Before a handoff or pause that needs durable state, update the project's
existing task card or handoff record in its authorized location. Reuse the
required format. These five details are usually enough:

1. Objective and responsible agent: Peter or Aster, following current
   assignment.
2. Last verified result: link the artifact or command result and its scope.
3. Current action: one concrete operation and its file or command location.
4. Open work: prerequisites, blockers, deferred checks, and what is unverified.
5. Resume here: the next record to read and the smallest useful action.

Treat the note as a record to verify on reentry. A historical PASS is not a new
test run. Do not create a second task card, move required records, or write into
read-only inputs to satisfy this style.

If work remains in your authorized scope, continue it. If the next action needs
the user, name that action precisely. If the task is complete, end with the
verified outcome; do not manufacture another step. Explanations and required
engineering evidence can be as detailed as the task needs.
