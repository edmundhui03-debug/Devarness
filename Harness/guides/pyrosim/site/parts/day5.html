Day 5

Today you start the solver, watch it work, and read what it wrote down

2–3 htime today
Goal

One finished FDS run of your own room, plus enough of its log and its CSV files read to say whether the run is worth keeping.

Learn

PyroSim has been building an FDS input file for four days. Today it hands that file to FDS, and FDS does the physics. Everything you watch from now on is FDS talking; PyroSim starts it, shows you its log, and opens the results afterwards.

There are two launchers, and they are not the same thing. Run FDS starts one FDS process. Thunderhead's own wording is that simulations launched this way can use multiple OpenMP threads, but will not use multiple MPI processes. Run FDS Parallel starts several FDS processes and gives each one its own mesh.

The rule that decides between them is short: one MPI process per mesh, and never more processes than meshes. Ask for more and FDS stops before it starts, with ERROR(112) and the message "The number of MPI processes, 2, exceeds the number of meshes, 1". That message was reproduced on the Mac used for this guide. The second half of the rule is about the machine rather than the model: do not ask for more processes than the desktop has logical processors.

  • The room you built has two meshes — the room and the box outside the door — so Run FDS Parallel can use two MPI processes.
  • A model with one mesh gains nothing from the parallel launcher. Use Run FDS.
  • Spare cores go to OpenMP threads instead. The FDS User's Guide is blunt about what that buys: "Typically, the use of OpenMP speeds the calculation by at most factor of 2."

More processes is not automatically faster, and the ceiling is set by your machine rather than by your model. The guide's own Mac was measured on exactly this case, 10 cm cells and 46,656 of them, changing nothing but the number of meshes:

MeshesMPI processesWall clock for 4 s of fireAgainst two
2221 sthe configuration this guide ships
4415 s1.4× faster
6619 sslower than four
8824 sslower than two

That machine reports eight cores, but four of them are efficiency cores and four are performance cores. MPI processes advance in step and exchange data at every time step, so the moment one process lands on a slow core it sets the pace for all of them. Eight processes came out worse than two. The number to match is the count of real cores, and the only way to know it is to measure.

If you split a mesh for speed

Splitting a mesh to get more processes is a change to the model, not only to the schedule. On this case the four-mesh split read about 3 % hotter at the ceiling than the two-mesh original, at every sample over two minutes — small, well inside the model uncertainty FDS itself reports, and far smaller than a change of cell size, but consistent and therefore real. If you split for speed, say so when you report the result, and do not compare a split run against an unsplit one as though only the clock had changed.

What MPI and OpenMP actually split

MPI splits the model. Each process owns whole meshes, holds them in its own memory, and swaps boundary data with its neighbours at every time step. That is why the count is tied to meshes and not to cores: a process with no mesh has nothing to do.

OpenMP splits the work inside one process across threads on the same machine. It needs no extra meshes, and it helps much less. PyroSim sets the counts itself — up to four threads for Run FDS and one for Run FDS Parallel — and Thunderhead recommends not changing them.

There is a consequence worth remembering on a shared office desktop. Thunderhead's own advice is that you may get more total work finished faster by running four simultaneous four-mesh problems on sixteen cores than by throwing everything at one job. On Day 7, when you want many runs rather than one fast run, that is the whole game.

Where the run lands is decided by where you saved the model. PyroSim creates a sub-directory of the current PyroSim file: the documentation's example is that a model saved as C:\pyrosim_files\switchgear.psm puts its results in C:\pyrosim_files\switchgear. The exported .fds file, the geometry files and every output FDS writes all go there. The slice and 3-D smoke files dwarf everything else in that folder, so choose the disk deliberately rather than by accident.

Watch out

Do not save the model inside OneDrive, or on a network drive. The FDS User's Guide states it plainly: "Saving files to a network share or a folder controlled by a cloud service (e.g. OneDrive) can result in simulation failures if a network issue or a file lock during automated backup results in Windows preventing FDS from writing data to a file." The run is writing to those files continuously for hours, so a single lock during a sync can end it.

On a managed office build, Documents is often redirected into OneDrive without saying so. Check the real path before you run, not after. The related symptom is forrtl: severe (47), a write to a read-only file; the documented answers are to run from a folder on a drive physically attached to the machine and outside system folders, and, as a last resort, to add FLUSH_FILE_BUFFERS=F to the &DUMP line.

The window that opens when the run starts is titled FDS Simulation - <your file>.fds. The Fundamentals tutorial calls it "the Run dialog"; the title bar is the software's own name, and where the two disagree the software wins. It carries a log pane that repeats what FDS prints, a Progress bar, Time Elapsed, Time Remaining, a Show results when finished checkbox, and the buttons Kill, Stop, Show Results, Save Log and Open Folder. You can minimise it and carry on using PyroSim, and you can even start another simulation.

Stop and Kill are not two words for the same button. Stop writes a .stop file that signals FDS to stop and also writes a checkpoint file, which often takes a noticeable moment; Resume FDS on the Analysis menu can then continue the run with a restart flag. Kill terminates FDS immediately and you will not be able to resume. Use Stop unless the run is producing nonsense and you want it gone. One trap follows from it: a .stop file left in the folder stops the next run with ERROR(109), telling you to remove that file. Delete it, or resume instead of starting again.

Treat a resumed run as a convenience, not a guarantee

The FDS User's Guide describes restart as "a fragile construct". It works, and it has saved long jobs, but a resumed run is not the same object as a run that went from start to end in one go. For the reference case in this guide, and for anything you will report, prefer one uninterrupted run.

Build

Run the short pilot first, then the real thing. The FDS User's Guide gives the same order for a different reason: "Initial calculations ought to be meshed coarsely so that the run times are less than an hour and corrections can easily be made without wasting too much time."

  1. File › Save — save the model into a folder on a local drive, outside any synced folder, with no spaces in the folder names. Keep the file name to letters, digits and underscores: a period in the job name stops FDS at set-up with ERROR(108), "No periods allowed in CHID". A space is not caught by that check, but the FDS User's Guide asks for none either, in the job name or in any directory above it. If the model is already sitting in a synced folder, close PyroSim, move the folder in Windows Explorer, and open it from its new home.

  2. File › Preferences › FDS — confirm Auto-Save PyroSim Model Before Running FDS is ticked, so a crash cannot take the last hour of edits with it. On the same tab, Parallel Execution Settings decides how many MPI processes the parallel launcher asks for: Create Process for Each Mesh, or Limit Processes Based on Logical Processor Count, which is the default.

  3. Analysis › Simulation Parameters › Time — set End Time to 60 s for the pilot. PyroSim's own default is 0.001 s and has to be changed for any run to do anything.

  4. Analysis › Run Model Checks — read what it reports before you start the solver. It costs seconds and it catches things the input file would only complain about later.

  5. Analysis › Run FDS Parallel — for the two-mesh room. With a single mesh use Analysis › Run FDS instead. Either one is also on the green play button on the File toolbar and its drop-down.

  6. Watch the FDS Simulation window while the pilot runs. Read the log rather than the progress bar: FDS prints a diagnostics block every 100 time steps, and warnings appear there first. Time Remaining is PyroSim's estimate rather than a measurement, so size the long run from the pilot below rather than from that field.

  7. When it finishes, press Save Log and keep the text file beside the run. Then press Open Folder and open <job>.out. The last two lines before the status line give Time Stepping Wall Clock Time and Total Elapsed Wall Clock Time, both in seconds. That number, not the progress bar, is what you scale from.

  8. Set End Time to 1200 s and run again. Expect the estimate from the pilot to be rough: FDS changes its time step as the flow speeds up, and the fire is three times larger in the second half of this programme than in the first.

Learn

A finished run leaves a folder with dozens of files in it. Six of them matter today.

FileWhat it holds
<job>.outThe diagnostics log. What FDS thought you asked for, a block every 100 time steps, and the final status line.
<job>_devc.csvEvery device, one column each, one row per device output interval.
<job>_hrr.csvHeat release rate and the energy budget, plus one pressure column for each pressure zone if any exist.
<job>_steps.csvTime Step, Wall Time, Step Size, Simulation Time and CPU Time — one row per printed diagnostics block, not one per step. The reference run wrote 508 rows for 48,968 time steps.
<job>_cpu.csvWhere the wall clock went, per MPI rank and per routine.
<job>.smvThe index file. This is what Results and Smokeview open; the slice, smoke and boundary files beside it are the bulk.

Two viewers can open that .smv file, and they are different programs. PyroSim Results is Thunderhead's viewer and needs a PyroSim or Pathfinder licence; it opens on its own at the end of a run when Show results when finished is ticked, or when Run Results When FDS Simulation Completes is on in the FDS preferences. Otherwise open it from the Results menu with View Results and pick the .smv. Smokeview is NIST's viewer, it ships with FDS, and it never opens by itself — use Open Smokeview on the Results menu. One asymmetry catches people out: the .pyrogeom geometry file PyroSim writes is not viewable in Smokeview.

In Results, the device and HRR CSVs are loaded for you, under the XY Plot Data group, so the curves are there without importing anything. For plots without leaving PyroSim, use View Time History Results on the Results menu and choose the CSV, or the drop-down arrow beside the plot icon on the File toolbar, which offers Plot Device Results, Plot Thermal Results and Plot Control Results. Only <job>_devc.csv, <job>_hrr.csv and <job>_ctrl.csv are expected to work there; <job>_cpu.csv does not display. In the plot window, Image Capture on the File menu saves a picture for your notes.

The tutorial and the software disagree on one menu name

The Basic Data Output tutorial calls the action "View Time History Plots". No such string exists in the 2026.1 software; the action is View Time History Results. Where a document and the program disagree, follow the program. The same tutorial series has a handful of these slips; where this guide gives a click-path, it gives the software's string.

Both CSV files have the same two-row header, and it surprises every spreadsheet on first contact. Row 1 is units. Row 2 is names. Data starts at row 3. These are the first eight columns of the reference run's device file, exactly as FDS wrote them.

RowWhat FDS writes there
Row 1s,C,ppm,1/m,m,,%,%
Row 2Time,"S1_T","S1_CO","S1_OD","S1_VIS","S1_FED","S1_O2","S1_CO2"
Row 3 onwardOne row per output interval, first column the time in seconds.
  • The empty field between the two commas in row 1 is real. FED has no unit, so FDS writes nothing there.
  • Your spreadsheet will treat row 1 as the header and the names you want will sit in the first data row. Name your series from row 2 by hand, and keep row 1 for the axis label.
  • The reference case sets a device interval of 1 s, so it writes one row per second. Each value is time-averaged over the preceding interval by default, not sampled at that instant.
  • Past 254 columns FDS splits the file into <job>_1_devc.csv, <job>_2_devc.csv and so on. If a device you expected is missing, look for a second file before you blame the model.

Now the .out file, which is where an experienced modeller looks first. Three things, in this order.

One: the last line. It is a single sentence and it tells you whether anything else in the folder is worth reading.

Last line of <job>.outWhat it means
STOP: FDS completed successfullyFDS reached your End Time and shut down cleanly. This is the only line that means the run finished.
STOP: Set-up onlyEnd Time was 0 s. FDS built the model, checked it and stopped. Useful on purpose, confusing by accident.
STOP: FDS stopped by userThe Stop button, or a .stop file. A checkpoint exists, so the run can be resumed.
ERROR: FDS was improperly set-up - FDS stoppedThe input file was rejected. Often there is no .out file at all, and the reason is only in the log.
ERROR(374): Numerical Instability - FDS stoppedThe solver gave up part-way. Day 6 covers how to find where and why.
ERROR: Unrealizable mass density - FDS stoppedAnother stop while the run was in progress. Do not treat it as a completed run.

Read that line rather than trusting the program's exit status. On the Mac used for this guide, FDS returned an exit status of zero for a successful run, for set-up failures and for a numerical instability alike. Windows exit codes were not tested for this guide, so treat them with the same caution. And when FDS rejects the input while reading it, it writes no .out file: the message went to the run window only, which is the reason Save Log is worth pressing every time.

Two: the last time-step block. FDS prints one every 100 steps. It gives the step number, the step size in seconds, the total simulated time in seconds, the pressure iterations, the maximum velocity and pressure errors with the mesh and cell where they occurred, and then, per mesh, the maximum CFL number, the maximum and minimum divergence and the maximum VN number. A healthy last block has the total time equal to your End Time, a step size close to the value the run settled on rather than orders of magnitude below it, and a maximum CFL number below about 1 — FDS adjusts the step to hold CFL between 0.8 and 1. Do not expect the settled step to match the initial time step printed near the top of the file: the reference run starts at 0.184 s, falls to about 0.03 s within the first ten seconds, and ends at 0.015 s, which is normal. A step size that has collapsed by orders of magnitude, next to a CFL number in the hundreds, is the signature of the instability on Day 6.

Three: search the file for "Pressure Zone". In a room with a door to the outside, there should be nothing to find; the 20 cm reference run has no such section. If you do find a Pressure Zone Information heading with a volume in cubic metres and a cell count, FDS has decided part of your model is sealed. FDS assumes any space is perfectly sealed unless you tell it otherwise, so the pressure inside rises, air stops flowing through the door, and an extra pressure column appears in <job>_hrr.csv — and none of this raises an error. The usual causes are a door hole that did not cut all the way through the wall, and an outside mesh with no open boundary vents.

The rest of the header is worth ninety seconds

The top of <job>.out repeats what FDS believes you asked for: the FDS revision string, the number of MPI processes, the cell counts and physical dimensions of every mesh, the total number of grid cells, the maximum cell aspect ratio, the initial time step, the end time and the ambient temperature. Comparing that against what you meant to build catches a wrong mesh or a forgotten parameter before you spend two hours computing with it.

Build

  1. Results › View Time History Results — open <job>_hrr.csv and plot the HRR column first. Nothing else matters until the fire is the size you specified.

  2. Open <job>_devc.csv the same way and plot the corner thermocouple tree, then the layer height and the upper and lower layer temperatures.

  3. Open <job>.out in a plain text editor. Press the End key, read the final line, then read the block above it.

  4. Search that file for Pressure Zone. Finding nothing is the result you want.

  5. Open both CSV files in a spreadsheet and look at the two header rows with your own eyes, so the layout is familiar before Day 7 asks a script to read them.

  6. In the plot window, File › Image Capture — save the HRR plot and the tree plot into the run folder. They are your record of what this run said on this day.

Check

Here is the run to compare against. Same room, same burner programme, 20 cm cells, FDS 6.10.1, the full 1200 s. The burner holds 100 kW to 600 s, ramps to 300 kW over the ten seconds after that, and holds 300 kW to the end, so 590 s is the last reading of the small fire and 620 s is ten seconds after the new level is reached.

Those are six sampled seconds out of 1200. The run's own _devc.csv file carries every column at every second, and that is what to plot against.

Read the heat release rate first. It reports the heat actually released by combustion in the gas, not the number you typed, so it wanders a little around the value you asked for: 109 kW and 102 kW against a nominal 100 kW, and 323 kW and 317 kW against 300 kW. If your own HRR sits at a third of the nominal, or at three times it, the burner area or the value per unit area is wrong, and Day 3 is where to fix it. Notice also how much the reported value swings once the fire is large: 255 kW at 620 s, 338 kW at 630 s, 359 kW at 800 s. That is turbulence, not a lag — the prescribed fuel flow is already at its full rate by 610 s, and the mean from 700 s to 1200 s is 298 kW against the 300 kW asked for. Judge the size of a fire from a few minutes of the curve, never from one second of it.

The tree is the clearest picture of what a compartment fire does. Within the first minute the four traces separate and stay separated: hot gas collects under the ceiling, while the 0.25 m trace near the floor has moved from the 20 °C ambient to only 24 °C by 60 s. That separation is the hot layer. At 600 s every trace steps up and the upper ones step most, which is what you expect when the fire triples and the extra heat goes into a layer that is already there. By 1195 s the floor trace has reached 51 °C against the ceiling's 342 °C — a rise of 31 K against 322 K — and that gap is the sign that cool air is still flowing in under the door, which is the other half of the same flow.

The ceiling thermocouple keeps climbing after the heat release rate flattens: 246 °C at 620 s, 311 °C at 900 s, 342 °C at 1195 s, while the fire holds near its 300 kW setting. Nothing is wrong. The lining is still warming up, and 0.1 m of aerated concrete absorbs heat for a long time, so the gas keeps warming with it. This run has not reached a steady state by 1200 s, and saying so is part of reporting it honestly.

The layer height falls in the first minute and then sits around 0.89 m above the floor for the rest of the run, wandering between 0.70 m and 1.05 m and showing no lasting change at the step at 600 s. It holds because the doorway vents more as the layer gets hotter, not because the fire stopped making smoke. Treat that number with care, though: FDS does not compute a layer interface. It integrates temperature along the vertical line you placed and reduces it to a height and two temperatures, using a method built for two-zone models. The FDS Validation Guide says as much — a layer height and a hot gas layer temperature are constructs of two-zone models, not things a CFD model calculates directly.

The floor heat flux is the number that grows fastest: 0.36 kW/m² at the start, 0.64 kW/m² at the end of the 100 kW stage, then 2.9 and 3.7 kW/m² in the second half. Radiation from a hot layer rises roughly with the fourth power of its absolute temperature, so doubling the layer temperature does far more than double what the floor feels. Meanwhile the tenability numbers move slowly: FED, which is the fraction of an incapacitating dose accumulated so far, reaches 0.03 at 900 s and 0.04 at 1195 s, and oxygen is still 18.2 % at 1195 s. Both sit at the 1.85 m node, not at the ceiling, and so does the visibility. Visibility is the one that degrades early: it holds at the 30 m clear-air maximum FDS reports by default until about 12 s, is below 5 m by 38 s, and drops to about 3 m after the step.

One honest caveat before you compare. These are 20 cm results, and 20 cm is coarse for this fire: the ratio of characteristic fire diameter to cell size is about 1.9 at 100 kW and 3.0 at 300 kW, below the 3.8 to 14 range NIST itself used when validating FDS against ISO 9705 room tests. The run reads low because of it. The MQH hand calculation for this room puts the 100 kW layer at 229 °C to 251 °C with a corner burner, Dillon measured about 305 °C at 2.35 m in a real ISO room at 100 kW, and this run gives 147 °C. At 300 kW those three figures are 555 °C to 621 °C calculated, about 615 °C measured, and 342 °C here. So use this table to check that your curves have the right shape and the right order of magnitude, and let Day 6 settle what the mesh is doing to the numbers.

Check your result

You are done for today when four things are true. The last line of <job>.out reads that FDS completed successfully. The last time-step block reaches your End Time with a sensible step size. A search for "Pressure Zone" finds nothing. And the HRR column sits near the value you specified, with the step at 600 s in the right place.

A run that passes all four can still be wrong — wrong lining, wrong yields, a device in the wrong cell. Day 6 is about that gap. What today buys you is the ability to tell a run that finished from a run that worked.

Your model has two meshes and the desktop has sixteen logical processors. How many MPI processes can you use, and what do the other cores do?

Two, one per mesh. Asking for more stops FDS with ERROR(112), "The number of MPI processes, 2, exceeds the number of meshes, 1", with your own counts in place of those. The spare cores can only be used as OpenMP threads, which the FDS User's Guide says speed a calculation by at most a factor of two.

Your PyroSim file sits in Documents, which is synced to OneDrive. What goes wrong, and where would the run have written its files?

PyroSim writes the run into a sub-directory beside the model file, so every output would have landed inside the synced folder. A file lock during an automatic backup can stop Windows letting FDS write, and the run fails part-way through with no fault in the model. Move the model to a folder on a drive physically attached to the machine.

The last line of the log says FDS completed successfully. Name two things that can still be wrong with the run.

Several are possible: a Pressure Zone listed in the .out file, meaning the room is sealed and the door never opened; an HRR column nowhere near the fire you specified; soot and carbon monoxide yields left at zero, so visibility and CO never move; a device placed outside every mesh. None of these raises an error, and the program's exit status is zero either way.

In <job>_devc.csv, what is in row 1, row 2 and row 3?

Row 1 is the units, starting with s for the time column, and a field can be empty where a quantity has no unit, as FED does. Row 2 is the names: Time, then each device ID in quotes. Row 3 is the first data row.

You need the machine for something else. Which button lets you carry on later, and what does it leave behind?

Stop. It writes a .stop file and a checkpoint, and Resume FDS on the Analysis menu continues from there. Kill ends the run immediately with no way back. Remember to clear the .stop file afterwards, or the next run stops with ERROR(109).
