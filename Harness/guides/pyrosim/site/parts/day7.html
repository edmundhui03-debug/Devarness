Day 7

Build a dataset from validated cases and raw sensor frames

2–3 htime today
Goal

By the end of today you have six valid room-fire variants with a manifest that says what each one is, a batch you checked rather than assumed, and a CSV of 5-second sensor data frames converted from a finished run.

Learn

The exporter defines a small educational CSV format: raw channels with explicit units, one row per sensor position every 5 s. Choose a downstream data format separately for your own project.

ChannelUnitWhere it comes from
temperature_c°CA THERMOCOUPLE device at the position the physical node would occupy
optical_densityper metreAn OPTICAL DENSITY device at the same point
co_ppmppmA VOLUME FRACTION device with SPEC_ID='CARBON MONOXIDE' and CONVERSION_FACTOR=1.0E6

Four more clauses decide the shape of the file rather than its columns, and each of them changes what you do today.

  • One frame every 5 s. The educational exporter selects the nearest raw reading at each five-second mark, starting at ignition.
  • By decimation, never by averaging. Keep the 1 s series and select every fifth sample so post-processing does not smooth the rate of rise.
  • t = 0 is ignition, not the start of the simulation and not wall-clock time. An onset offset is applied when the scenario is generated, never by shifting a finished series afterwards.
  • One incident is one fire, start to finish, on one floorplan, and the split between training and test data is by whole incident. Never split a rolling window, and hold out whole buildings for any claim about transferring to a new building.
Why decimation and not a 5-second average

A mean over five seconds is a low-pass filter. It removes the fast part of the signal, and the fast part is the forecast: a network trained to see temperature climbing at so many degrees per second cannot see it in a series that has been smoothed first.

FDS time-averages device output between printouts by default. Use TEMPORAL_STATISTIC='INSTANT VALUE' on the sensor channels and check the .out file. Selecting every fifth row does not undo averaging already performed by the solver.

Scenarios enumerate, and that is honest work for a handful of variants

PyroSim has a feature for variations of one model, called Scenarios, and it is worth knowing exactly what it stores. Thunderhead's documentation is direct about the limit: scenarios only explicitly track the enabling and disabling of objects, and to modify an object parameter in a scenario, the object must be duplicated, the parameter in the duplicate must be modified, and the original object must be disabled in the scenario.

Their own worked example shows the cost. To run the same room with a burner at 1000 kW/m² and again at 2000 kW/m² on a 1.0 m² vent, you copy the vent, create a second surface from the fire template, set its heat release rate, assign it to the copy, then disable the original in one scenario and the copy in the other. That is four objects to keep consistent for one changed number. Change four numbers at once, as today's batch does, and the duplicates multiply.

What Scenarios do well is the running. Export Scenarios writes each scenario's .fds file into its own subfolder beside the saved model, and writes a BAT file that can be double-clicked in Windows Explorer to run them all in sequence. The documentation also warns why you should use it rather than running scenarios one at a time from Run FDS: running individually overwrites the same results file every time. For five or ten hand-made variants, this route is the right one, and it needs no scripting at all.

For hundreds of runs, the file itself becomes the template

The other route treats the exported .fds file as text. You export one file from the model you have spent six days building, replace the values that vary with placeholders, and let a script fill them in. PyroSim stays the authoring tool; the script only substitutes numbers into a file PyroSim wrote.

The risk is that a generated file can be wrong in ways FDS does not object to, and Day 4 and Day 6 have shown you several. An obstruction too small for the mesh is rejected, and the guide is explicit that if at least two of the three obstruction dimensions are less than half of the corresponding cell dimensions, the obstruction is ignored. A vent must be a plane on a solid. Anything reaching past the mesh is cut off at the boundary. A device outside every mesh loses its column from the CSV with a console warning and nothing else. So the generator validates each variant before it writes a file, and refuses the ones that break those rules.

This is the template the guide ships. Every value in double braces is filled by the script, and the sensors are identical to the reference case, so every run in a batch is measured in the same places.

Build

The first five steps are the Scenarios route, done in PyroSim on the Windows computer. Do them once even if you plan to generate hundreds of runs later, because the BAT file that comes out tells you where FDS lives on that machine.

  1. Toolbar › Edit Scenarios — the Scenarios box on the main toolbar holds the active scenario drop-down and the Edit Scenarios button beside it. Click New, give the scenario a name in plain ASCII letters, and choose what it is Based On. Make two: one for the fire you already have, one for a second version of it.

  2. Navigation tree › right-click the burner vent › Copy/Move — in the Translate dialog select Copy mode and click OK to duplicate it. Then create a second burner surface with a different heat release rate per area, using your existing surface as its template, and assign that surface to the copy. Nothing else in the model changes.

  3. Right-click a selected object › Disable Object(s) — with the first scenario active, disable the copy. Switch scenarios with the toolbar drop-down and disable the original instead. A disabled object disappears from the 3D view and is struck through in the tree. Enable/Disable Object(s) per Scenario on the same context menu shows the whole picture at once.

  4. File › Export › Export Scenarios — PyroSim writes one subfolder per scenario where the model file is saved, each holding that scenario's .fds file, plus a run file named run_scenarios-<model name>.bat. An Explorer window opens with it highlighted.

  5. Windows Explorer › the exported folder — open the BAT file in a text editor before you run it. Its SET PATH lines name the FDS folder inside your PyroSim installation, and that path is the one to reuse in any batch you write yourself. The tutorials show older version numbers in it, so read yours rather than copying theirs. Then double-click the file to run the scenarios in sequence.

The remaining steps are the template route. Copy the guide's tools and cases folders side by side into one local folder on the desktop, and run the commands from the folder that contains them both. The script finds the template by walking from its own location, so keeping those two folders together matters.

  1. File › Export › FDS File — enter a file name and click Save. PyroSim's note on this page is worth heeding: a string with non-ASCII characters is converted into a numeric hash in the FDS input file, which can make input files and CHIDs appear as numbers. Keep model and object names to plain letters, digits and underscores.

  2. Model view › Record View — read the exported file against the template above. Model Records is a read-only exact copy of the file that will be input into the FDS simulator, so this is where you confirm which lines your own model writes for the burner, the door hole and the devices, and which values you would want a script to vary.

  3. Generate the variants. In a command prompt in that folder, run python tools/make_scenarios.py --n 6 --seed 7 --cell 0.2 --t-end 1200 --out results/batch. Use whatever command starts Python on that machine. It writes six .fds files and a manifest.csv into results/batch, and nothing else; the script uses the Python standard library only.

  4. Read the manifest before you run anything. Open manifest.csv and check one row by hand. The first variant of that seed is a 300 kW medium-growth fire with its burner corner at 2.4, 0.0 m and a 0.4 m door: a 0.6 × 0.6 m burner top is 0.36 m², and 300 kW ÷ 0.36 m² is the 833.3 kW/m² the manifest reports. Run the same command with the same seed again and you get byte-identical files, which is what makes a batch reproducible.

  5. File › Import FDS/CAD File — take one generated file back into PyroSim and look at it in 3D. During import PyroSim checks the validity of each record and notifies you if errors are detected, so this is a second opinion on the geometry as well as a way to see where the burner landed. Import supports FDS versions 4, 5 and 6.

  6. Run the batch. Copy the pattern from your exported BAT: set the PATH to your PyroSim fds and fds\mpi folders, set OMP_NUM_THREADS=1, then run one FDS process per variant. The generator writes the six files flat into results/batch rather than one folder each, so either run them where they sit — the CHIDs differ, so no output collides — or move each into its own folder first, which is what the BAT's PUSHD lines do. Keep the files on a drive physically attached to the computer; the FDS guide warns that saving to a network share or a cloud-synced folder such as OneDrive can cause simulation failures.

  7. Check every log before you believe the batch. Search each run's log and .out file for the exact final line STOP: FDS completed successfully, and flag any line containing ERROR(, any WARNING: DEVC, and any unexpected Pressure Zone Information. The Watch out box below says why the exit status cannot do this job for you.

  8. Convert one run to sensor frames. Run python tools/fds_to_dataset.py results/batch/room_000_devc.csv -o results/batch/room_000_frames.csv. The standard-library exporter writes raw readings and validates sampling and CO units; it assigns no risk or safety labels.

What the two scripts do, and what they refuse

make_scenarios.py varies four things a real room fire varies: the peak heat release rate, chosen from 100, 200, 300, 500, 750 and 1000 kW; the growth class, one of the four standard t-squared curves, slow, medium, fast and ultra-fast, which reach about 1054 kW in 600, 300, 150 and 75 s; the burner's position anywhere on the floor grid; and the door width from 0.4 m to 1.2 m. A bigger fire is drawn as a wider burner rather than a hotter one, aiming at roughly 1000 kW/m², and the growth class plus the peak become a negative TAU_Q — for that first variant, −160.0 s.

It refuses more than it accepts, which is the point. A variant is rejected if the burner corner or either door edge is off the cell grid, if the burner reaches outside the room or through the front wall, if the peak falls outside 50 to 2000 kW, or if the burner would sit on top of the floor heat-flux gauge at 1.85, 1.25 m or the layer-height line at 3.25, 2.15 m. The last of those is the one a person would miss: the file would run to completion and quietly return a floor flux measured through the burner.

fds_to_dataset.py reads units and device names from the two FDS header rows. It keeps the reading nearest each five-second mark and emits time_s, zone, temperature_c, optical_density, co_ppm, visibility_m and fed. CO is converted from ppm, mol/mol or %; unknown units, gaps and non-finite values are rejected.

Check

Check your result

Open the converted file and check four things. The first row is at 0.0 seconds. The spacing between frames is exactly 5.0 s, with no gaps. There are two rows per frame, one for each sensor node. And for a 1200-second run there are 241 frames per zone, which is 1200 ÷ 5 plus the frame at zero; anything less means rows were dropped or the run ended early. Then look at the co_ppm column: it should read in tens or hundreds, not as a fraction like 0.00006, which would mean a volume fraction reached the file without being scaled.

Converting the guide's own reference run is the quickest way to see that the numbers survive the trip. Sensor node S1 in that 20 cm run gives these frames, and they are the same values the reference table quotes, arriving in the contract's units:

Watch out

FDS returns an exit status of 0 even when it has failed. On the historical reference environment the binary returned 0 after every set-up error and after a run-time error, and PyroSim's own launcher logs a subprocess exit of 0 after a numerical instability. A batch script that tests the exit status will therefore report a clean sweep over runs that produced nothing. The only reliable test is the text: the final line STOP: FDS completed successfully. Add to it a search for ERROR( and for WARNING: DEVC, because a device outside the mesh costs you a channel in every run of the batch and says so only once, on the console.

One more failure is specific to batches: the name. The FDS guide states that it will over-write the output files of a given case if its assigned name is the same, and that the job name must contain no blank spaces. A period in the CHID is rejected outright with ERROR(108), so a variant called hrr_0.5MW never starts. Give every variant its own CHID — the generator uses room_000 upwards — or the second run quietly erases the first.

What a batch costs, and what published work actually used

Run one case before you queue fifty. The FDS guide's advice is to run your job for a short amount of time to estimate the time required for the full job, and setting T_END to zero performs only the set-up work so you can check the geometry in Smokeview for the price of a few seconds.

Historical timings are illustrative and do not predict your computer. Measure a short pilot run before planning a batch. Several small cases may use available cores more effectively than assigning every core to one case; compare both options locally.

It helps to know what published work in this field ran, because two of the famous numbers are not FDS numbers at all.

StudyCasesEngine and cost
P-Flash, Wang et al. 20211 000CFAST, a two-zone model, not CFD. The paper's own convergence check found flashover prediction stopped improving at about 1000 cases
FlashNet, Tam et al. 202278 000CFAST again, on about 250 cluster nodes over roughly two weeks
Su et al. 2021280FDS. 15 to 48 h per atrium case on about 32 cores

The pattern is the one to carry into any plan you write: the tens of thousands of cases belong to zone models, which solve two well-mixed layers per room in seconds, and the CFD campaigns are in the hundreds. Whatever you promise a supervisor, promise it in hundreds of FDS cases and a sampler, not in tens of thousands.

The honest limit of what you built today

This is an educational pipeline rehearsal. S1 and S2 are two sensor positions in one room, not connected compartments. These cases establish neither transfer to unseen buildings nor an evacuation or safety assessment. Validate any scientific application independently.

The next step is not more runs of this room. It is a second compartment and a doorway between them, so that a zone graph exists at all, and a design-fire source for the peak heat release rates rather than a range borrowed from residential studies. Both are decisions for the project, not for the simulator.

FDS can write device output every 5 s directly. Why does this guide write it every 1 s and keep every fifth row?

FDS time-averages device output by default. Select every fifth 1 s row to keep a five-second sequence without additional smoothing, and set TEMPORAL_STATISTIC='INSTANT VALUE' on sensor channels to prevent solver averaging. Confirm the setting in the .out file.

You want 24 variants that differ in peak heat release rate, growth rate, burner position and door width. Why are PyroSim Scenarios the wrong tool, and what do you use instead?

A scenario only enables and disables objects. Changing a parameter means duplicating the object, editing the duplicate and disabling the original in that scenario, so every changed number adds objects to keep consistent across all 24. Export one FDS file instead, turn it into a template, and let a script fill and validate the values. Scenarios remain the right tool for five or ten hand-made variants, and their Export Scenarios BAT is still a good model for the batch runner.

Your batch of 40 runs finished overnight and every process returned exit status 0. Why is that not evidence of anything, and what do you check instead?

FDS returns 0 after set-up errors and after run-time errors alike, so the status says only that the program ended. Search each log for the final line STOP: FDS completed successfully, and flag any ERROR(, any WARNING: DEVC line, and any unexpected Pressure Zone Information, which is how a sealed room announces itself.

Two variants in a batch were written with the same CHID. What do you find afterwards?

One set of results. FDS over-writes the output files of a case whose assigned name is the same, so the second run erases the first and both entries in your manifest point at the survivor. Give every variant its own CHID, with no spaces and no periods — a period stops the run with ERROR(108).

Name two claims this one-room dataset cannot support, however many variants you generate.

Anything about the zone graph, because one compartment has no adjacency and the two nodes are positions in the same volume; and anything about transferring to an unseen building, which needs whole buildings held out of training. It also carries no occupancy channel, since a crowd simulator owns that one.
