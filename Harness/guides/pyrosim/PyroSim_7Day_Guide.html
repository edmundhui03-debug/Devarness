Start here

PyroSim does not calculate the fire, and knowing that changes how you learn it

PyroSim is an editor. It draws the room, holds the burner and the sensors, and writes them all into a plain text file with a .fds extension. That file goes to FDS — the Fire Dynamics Simulator, written by NIST and free — which does every calculation. When people say "I ran PyroSim", what ran was FDS.

This matters for three reasons. The words you use in a paper are "an FDS simulation prepared in PyroSim", not "a PyroSim simulation". The thing to check when a result looks wrong is the text file, not the drawing. And on Day 7, when one room has to become hundreds of rooms, the text file is what a script can write and PyroSim cannot.

Day 1

PyroSim draws the room, FDS does the physics, and one text file passes between them

2–3 htime today
Goal

A licensed PyroSim you can drive on the Windows computer, a 60-second test fire that has run from start to finish, and the one line in its output file that proves FDS got to the end.

Learn

You are learning two programs today, not one. PyroSim is an editor made by Thunderhead Engineering: you draw the room in it, fill in dialogs, and it writes a text file. Fire Dynamics Simulator, FDS, is written by NIST: it reads that text file, solves the flow and heat transfer, and writes the results to disk. PyroSim never works out a temperature. It prepares the question and it draws the answer.

The two are shipped together. PyroSim 2026.1 is, in Thunderhead's words, "designed for FDS version 6.10.1", and it installs that exact build of FDS alongside itself, plus Smokeview 6.10.1 for viewing results. So the version of PyroSim on the Windows computer fixes the version of the solver your numbers come from.

The whole pipeline is five steps, and every day of this guide sits somewhere on it.

  • You edit a model and save it as a .psm file. That file belongs to PyroSim alone; it is binary, not text, so no script and no text editor can read it.
  • When you run, PyroSim writes your model out as a .fds file. This one is plain text, and it is the only thing FDS ever sees.
  • FDS reads the .fds file, checks it, and computes the fire.
  • FDS writes its own files back into the same folder: a log of the run, a file index for the viewers, and comma-separated tables of numbers.
  • PyroSim Results or Smokeview reads those files and draws smoke, slices and graphs.

The .fds file is written in a fixed form called namelist records. The FDS User's Guide defines it plainly: "Each namelist record begins with the ampersand character, &, followed immediately by the name of the namelist group, then a comma-delimited list of the input parameters, and finally a forward slash, /." Text outside a pair of & and / is ignored, which is why those files can carry comments, as long as nothing but a space comes before an ampersand. You do not have to write this language to use PyroSim, but you will read it every day from now on, because it is the only place where what PyroSim means and what FDS will do are the same thing.

Why the FDS version matters more than the PyroSim version

PyroSim 2026.1 and 2026.2 ship the same solver. The bundled fds.exe, fds_openmp.exe and smokeview.exe are byte-for-byte identical in the two release packages; only PyroSim's own launcher differs. Both carry the revision string FDS-6.10.1-0-g12efa16, which is the revision on the title page of the FDS 6.10.1 User's Guide.

That matters for sensor data. A result is reproducible if someone else runs the same input file with the same solver version, so record the FDS version next to every number you keep, not the PyroSim version. FDS 6.11.0 changed flux limiters, a corner boundary condition, the 3D smoke file format and thermocouple defaults, so a newer solver reading the same input file can return different numbers, and that is not a mistake by either side.

  • The View toolbar holds the camera views, the render drop-down (Solid with Outlines and four others), the navigation tools and a Group: drop-down. Beside it a filter toolbar shows and hides object types and offers Preview FDS Blocks, which you will use on Day 2.

  • The drawing toolbar runs down the left edge of the model view: slab, wall, room, hole, vent, device, slice and mesh tools.

At the bottom of the model view are three tabs: 3D View, 2D View and Record View. Add, remove or select an object in one and the others follow at once. The third tab is the one that matters most in this guide. Record View shows the FDS input file PyroSim is writing, kept up to date as you work, so you can watch a dialog turn into a line of &OBST or &SURF. It has two sections: Model Records, which is read-only because PyroSim generates it, and Additional Records, where you can type lines that are injected at the top of the file. PyroSim performs no validation on what you type there, and its own objects cannot refer to it, so leave it empty until Day 5.

Units next, because a wrong unit is the cheapest mistake to make and one of the hardest to spot. PyroSim can display and accept either metric or English units: click SI or EN on the File toolbar, or use the Units item on the View menu. Switching converts the values you have already entered rather than reinterpreting them. Record View is the exception that keeps you honest: it always displays values in the units FDS uses, whatever the buttons say. Work in SI, which is what FDS reads and what this guide quotes throughout: metres, seconds, kilograms, degrees Celsius, and kilowatts for heat release rate.

Typing a unit into a field

Thunderhead documents typed units for PyroSim 2026.2: you enter a number with unit text after it, such as 2.75 m, 30 cm or 22 C, and the field converts when you press TAB or ENTER. The text is case-sensitive, and a composite like 4 ft 9 in is not accepted. The same page does not exist for 2026.1, so on a 2026.1 desktop treat this as untested: set the unit system first, then type plain numbers.

Build

Work through these in order. If PyroSim has to be installed or updated by your IT team rather than checked, note that installation needs administrator rights, that installing a new version removes the older one while keeping your licence and property files, and that the installer adds Windows Defender exclusions for the bundled FDS executables so runs are not slowed down.

  1. Start PyroSim. If the Licensing and Activation dialog opens on its own, the machine is not licensed yet. You can open the same dialog at any time from Help › License.

  2. Licence the machine the way your office licence works. For a node-locked licence, either choose Enter an online activation key and type the 22-character key, which looks like AA00-BB11-CC22-DD33-EE44-F5, or, if the desktop has no internet access, copy the 7 to 8 character HostID shown in the dialog, generate a .lic file at Thunderhead's activation page on another machine, and choose Use an existing license file. For an office floating licence, choose Floating License Server, then Edit floating license settings, and enter the server host name with port 52100.

  3. Confirm which release you have, because two labels differ. Open the Help menu: the licence item reads Remove License… on 2026.1 and Clear License Cache… on 2026.2. The same menu carries the five manuals that ship with the software, including the FDS User Guide and the FDS Technical Reference. Open the FDS User Guide once now so you know it is there; it is the reference behind most of this guide.

  4. Set two preferences. On File › Preferences › General, tick Record Preview, which adds a preview pane to many dialogs showing the text that dialog will produce in the FDS input file. On File › Preferences › FDS, tick Auto-Save PyroSim Model Before Running FDS; without it, PyroSim does not save your model to disk when you run, so a crash during a run can cost the edits you made before it.

  5. Click SI on the File toolbar so the whole session is metric. The equivalent menu route is View › Units.

  6. Make an empty model with File › New, then open Analysis › Simulation Parameters and look at the Time tab. End Time reads 0.001 s. That is PyroSim's default and it has to be changed before any model will run for a useful length of time. The corresponding line in the file is the &TIME record, and the dialog's own preview pane shows it as &TIME T_END=1.0E-3/. Close the dialog without changing anything.

  7. Get a model that already works. Download Thunderhead's Your First Fire solution file, unzip it into a plain local folder, and open my_first_model-solution.psm with File › Open. It is a 660 kW fire in a 5 m × 5 m × 2.75 m room with a 1 m × 2.1 m doorway. If you would rather build it yourself, the steps are in the box below this list.

  8. Read the model through the Navigation panel rather than the picture. Expand Meshes, Surfaces and Reactions, and double-click one entry in each to open the dialog behind it. You are looking at the same model three ways: the tree, the 3D view, and the file.

  9. Click the Record View tab and read the file top to bottom. Find the &MESH line and its IJK cell counts, the &OBST lines for the floor, walls and ceiling, the &SURF line carrying HRRPUA, the &REAC line naming the fuel, and the &TIME line. You do not need to understand them yet. Notice only that everything you have seen in the dialogs is in here, and nothing else is.

  10. Set the run length at Analysis › Simulation Parameters › Time: End Time 60 s. On the same dialog's Environment tab, tick Ambient Temperature and enter 22 °C, which is the tutorial's value; FDS's own default would be 20 °C. Watch the &TIME line in Record View change when you click OK.

  11. Save with File › Save As into a local folder on the desktop's own disk, naming the model my_first_fire.psm. Avoid spaces and periods in the folder name and the file name, and do not save into OneDrive or a network drive. The reason is in the Watch out box below.

  12. Run it: Analysis › Run FDS, or the green triangle on the File toolbar. The FDS Simulation dialog opens. It shows FDS's own console output in a log pane, a progress bar, Time Elapsed and Time Remaining, a Show results when finished tick box, and the buttons Kill, Stop, Show Results, Open Folder and Save Log. Thunderhead's tutorial says this run takes a few minutes. Watch the log rather than the progress bar: that text is the only place some errors ever appear.

  13. When it finishes, open the run folder. PyroSim creates a sub-directory beside the .psm file and named after it, so my_first_fire.psm gives a folder my_first_fire, and every file FDS writes lands in it. Open my_first_fire.out in any text editor and go to the very end of the file.

Check

FDS tells you how it ended in its last line, and that line is the only reliable check. The message you want is STOP: FDS completed successfully, and FDS appends the job name to it, so the line reads STOP: FDS completed successfully (CHID: my_first_fire). It is written both to the run log you watched and to the end of CHID.out, where CHID is the job name, here my_first_fire. Two habits follow from how FDS behaves. First, FDS returns an exit status of 0 even when it has stopped on an error, so on Day 7, when runs are scripted, the completion line is what a script must test for, not the exit code. Second, an error found while reading the input file can stop FDS before it opens CHID.out at all; that message exists only in the console text, which is the run window's log pane, and Save Log is how you keep it.

The Results viewer opens by itself at the end of a run by default; the Show results when finished box in the run dialog and Run Results When FDS Simulation Completes on File › Preferences › FDS are what control it. If it does not open, use View Results on the Results menu. It uses the same licence as PyroSim. Smokeview never opens by itself; it is Open Smokeview on the same menu. Looking at the smoke is Day 5's work, so a quick look now is enough.

Watch out

Where you save the model decides where the run happens, so choose the folder carefully today. PyroSim runs FDS in a sub-directory beside the .psm file, and the FDS User's Guide warns that saving into a network share or a folder controlled by a cloud service such as OneDrive can fail a simulation part-way, because a file lock during an automated backup stops Windows letting FDS write. Names matter too: no periods or spaces are allowed in the job name, so a period stops the run with ERROR(108): No periods allowed in CHID, blank spaces in directory or file names break multi-computer runs, and non-English characters in names that reach FDS get converted to numbers. Keep to a local folder, plain English letters, digits and underscores.

Day 2
The mesh decides everything you can see


2–3 htime today




Goal
An ISO 9705 room in PyroSim built from two meshes of 20 cm cubes, with a 0.8 m × 2.0 m door punched right through the front wall, proved open by a one-second run.


Learn


FDS does not see a room. It sees a box of rectangular cells, and it solves the same set of equations once in every cell, every time step. That box of cells is the mesh. Everything you draw in PyroSim — a wall, a doorway, a burner, a thermocouple — is placed against that grid before FDS starts, and anything smaller than a cell is either snapped onto a cell face or dropped. So the mesh is not a setting you tune later. It fixes what the run is able to show you.


Two properties of a cell matter. The first is its shape. The FDS 6.10.1 User's Guide is direct about it: "It is best if the mesh cells resemble cubes; that is, the length, width and height of the cells ought to be roughly the same." PyroSim carries the same advice inside the Edit Meshes dialog, where each axis shows a Cell Size Ratio whose tooltip reads "Ratio of this cell dimension to the shortest. For best results, use cubic cells (ratio of 1.0)." Today every cell is a 0.2 m cube, so all three ratios read 1.00.


Halving cell size doubles the cell count along each axis: eight times as many cells. The smaller time step can raise computation further; Thunderhead describes roughly sixteen times the work for one refinement. Measure a short pilot on your own computer before scheduling the full programme.


There is a way to judge cell size that does not depend on the room. FDS defines a characteristic fire diameter D* from the heat release rate, and compares it with the cell size. Write the fire's heat release rate as Q in kW, and:

Where "4 to 16" came from, and why it is not a rule


The FDS 6.0.0 User's Guide of November 2013 carried a footnote saying that for the validation study sponsored by the US Nuclear Regulatory Commission — NUREG-1824, Stroup and Lindeman, 2013 — the D*/δx values ranged from 4 to 16. That footnote is the source of every "4 to 16" you will read on a forum. NIST removed it. The 6.10.1 guide now points at the table in the FDS Validation Guide instead and says of those values: "These values range over two orders of magnitude and were chosen based on a grid resolution study and the particular attributes of the given fire scenario. Taking any of these values as an 'acceptable' minimum is inappropriate."


The same guide says what to do in its place: "build an FDS input file using a relatively coarse mesh, and then gradually refine the mesh until you do not see appreciable differences in your results. This is referred to as a mesh sensitivity study." That is Day 6, and it is the only honest answer to "is my mesh fine enough".


For context, the Validation Guide's row for NIST's own ISO 9705 room experiments lists D*/δx between 3.8 and 14. Your 20 cm mesh sits below that. Report it that way rather than hiding it.




What "divisible by 2, 3 and 5" actually buys you


PyroSim warns when a cell count is awkward: "The number of cells is potentially inefficient. For maximum efficiency, the number should be factorable by 2, 3 and 5." It is an efficiency message, not an accuracy message, and the FDS guide explains why. The pressure solver uses Fast Fourier Transforms in the y and z directions only, so the habit applies to the J and K of the cell counts; "The number of cells in the x direction (the I in IJK) is not affected by this restriction". And then the guide undercuts it: "since the pressure solver uses less than 10 % of the total CPU time, the gains in using low prime dimensions are usually negligible."


Thunderhead's own first tutorial uses a 55 × 55 × 42 mesh, which breaks the advice and runs fine. Today's counts — 18, 12, 12 and 12, 18, 15 — all factor into 2, 3 and 5, so you should see no warning. If you ever do, treat it as a suggestion about speed.




One last thing before you draw anything, and it is the reason today's room needs so few obstructions. The FDS guide states: "By default, FDS assumes that the exterior boundary of the computational domain ... is a solid wall." A mesh is a sealed box unless you open it. That cuts both ways. It means a mesh drawn exactly to the room's inner dimensions gives you the back wall, the two side walls, the floor and the ceiling for nothing. It also means that the space outside the door will hold its smoke in and its pressure up unless you add OPEN vents on its outer faces.


Why a second mesh outside the door at all, rather than an OPEN vent across the doorway itself? Two reasons, both from the guide. An OPEN vent may only sit on the exterior boundary of the domain, so one placed on an interior wall stops the run with ERROR(819). And where the doorway flow is part of the answer, as it is here, the guide advises: "if the flow through the doorway or window is important, you should extend the domain a few meters rather than use an OPEN boundary." So the domain is extended 2.4 m past the door, and the open boundaries are moved out there.

Learn


There is no fire object in FDS. The User's Guide puts it plainly in section 9.1: a specified fire is modelled as the ejection of gaseous fuel from a solid surface or vent, with a heat release rate per unit area, HRRPUA, in kilowatts per square metre. You do not place a flame. You describe a patch of surface, say how many kilowatts each square metre of it gives off, and FDS pushes fuel gas in through that patch and burns it where it meets oxygen.


So a working burner needs two separate things, and they live in two separate dialogs. A reaction says what the fuel is and what it turns into. A surface says how fast fuel comes out and when. Miss the reaction and FDS refuses to start, with a message that names the surface: ERROR(314): SURF BURNER Must have a REAC line when using HRRPUA or MLRPUA. Miss a detail in either one and FDS usually runs to the end and gives you the wrong fire without complaining.


Why a fire is a boundary condition and not a prediction
FDS solves the gas in the room cell by cell. Fuel gas can only enter through the faces of cells, which is why a burner has to be a surface. The reaction then converts that fuel to heat, water, carbon dioxide, and whatever soot and CO you asked for, wherever fuel and oxygen mix.
One consequence is worth carrying into every report you write: this model does not predict how big the fire gets. You prescribe it. Johansson and Ekholm gave eight Swedish consultancies the same problem — an 800 mm heptane pool in a three-room apartment — and compared what came back, in Fire Technology in 2018. In their words, the differences in how the fuel and the burner were described were relatively large, which resulted in large differences in mass loss rate and heat release rate. The room physics was the easy part. The burner definition was where the answers diverged.


The reaction, and the trap in the library


From FDS 6 onward a reaction is compulsory for a fire, and the guide is explicit that you are responsible for the fuel chemistry and for the post-combustion yields of CO and soot, because those yields default to zero. Zero is a real number here, not a missing value: FDS will happily run a fire that makes no smoke at all.


PyroSim ships a property library with 21 predefined entries named FDS6 PROPANE, FDS6 METHANE and so on. Each of those entries sets the fuel and nothing else. Add FDS6 PROPANE from the library, change nothing, and every smoke channel in your results is dead flat for the whole run: the CO reading stays at exactly 0, optical density stays at 0, visibility sits pinned at its 30 m ceiling, and the fractional effective dose loses its carbon monoxide term entirely. The gas still gets hot, so the model looks alive while half of the educational measurements is missing.


Set two numbers on the Byproducts tab and the problem goes away: a soot yield of 0.024 and a CO yield of 0.005, both in kilograms per kilogram of fuel burned. Those are NIST's own values for propane. The FDS Validation Guide for 6.10.1 states in section 12.2.2 that in all cases the soot and CO yields were taken to be 0.024 and 0.005 respectively, based on the measurements of Tewarson, and NIST's validation input for an NFPA 286 room with a corner propane burner carries the same pair.


What those two yields do and do not change
The yields are fractions of fuel mass: 0.024 means 24 g of soot for every kilogram of propane burned. They apply to well-ventilated, post-flame conditions, which is what a 100 kW and 300 kW burner in an open-doored room gives you.
They barely change the heat. They decide the smoke. Soot yield drives optical density and visibility, because FDS turns soot mass into an extinction coefficient using a mass extinction coefficient of 8700 m²/kg. CO yield drives the CO reading and the CO part of the fractional effective dose. If you later model a different fuel, look the yields up rather than reusing these.


The surface, and the arithmetic that decides your fire


A burner surface carries one number that matters today: heat release rate per unit area, in kW/m². Total output is that number multiplied by the area you paint it on. PyroSim's own documentation gives the worked case: a surface with 500 kW/m² applied to a 2.0 m² vent produces a 1000 kW fire. Run it backwards to get what you type: divide the kilowatts you want by the square metres of burner top.


The ISO 9705 ignition source is a 170 mm square sand burner, so its top is 0.17 × 0.17 m = 0.0289 m². Your mesh cannot draw that. On the 20 cm grid you built yesterday the nearest honest shape is one whole cell, 0.2 × 0.2 m, which is 0.04 m² — about 38 % more area for the same kilowatts. The 10 cm version of the reference case draws that same square as four cells. Keeping the total heat right matters more than keeping the footprint right, so pick the flux that gives the right total on the patch you actually drew.

The programme, and the two ways to ramp


ISO 9705-1:2016 clause 6.4 sets the heat output: 100 kW for the first 10 minutes after ignition, then 300 kW for a further 10 minutes. That is 600 s and 1200 s, and it is why the reference run is 1200 s long.


FDS will not step from nothing to full output instantly unless you insist. Every burner surface has a ramp, and the default is a hyperbolic tangent with a time constant of 1 s, so the burner is at about 76 % of full output one second after the start. That default is fine for a single-stage fire and useless for a two-stage programme. There are two ways to change it.


    

  • A time constant. In the FDS file this is TAU_Q. A positive value gives the tanh curve above. A negative value gives a t-squared growth that reaches full output at the absolute value of the number and holds it there: TAU_Q=-300 means full output at 300 s. The 6.10.1 guide words this as "after TAU_Q seconds"; the 6.11.1 guide adds the absolute-value bars. PyroSim's ramp control is where you choose this.
    • 

  • A custom ramp. A list of (time, fraction) pairs. The fraction is the share of the HRRPUA you typed, FDS interpolates linearly between the points, and the times must increase. This is the only way to write the ISO two-stage programme, because it is two flat stages with a step between them.
    • 



The two are mutually exclusive. The FDS User's Guide says so in section 11.1: the TAUs and the RAMPs cannot both be used on the same quantity. In PyroSim you pick one from the Ramp-Up Time control on the burner's Heat Release tab, and picking a custom ramp opens an Edit Values table for the pairs.


One last decision before you draw anything: how high the burner sits. ISO 9705-1:2016 clause 6.2 puts the top surface (146 ± 3) mm off the floor, in the corner opposite the doorway wall, touching both walls. Under the 1993-era practice the same 17 cm burner was raised so that its top was 300 mm above the floor, which is how Dillon's 1998 NIST measurements were made. The reference case follows the 2016 edition, and each mesh takes the nearest cell face to 146 mm: 0.1 m on the 10 cm version, 0.2 m on the 20 cm mesh you are working in. That is not a choice you can dodge — run the 10 cm file on 20 cm cells and FDS snaps its 0.1 m burner top up to 0.2 m, which is what the reference run's own geometry shows. If you ever reproduce a pre-2016 test, move the top to 0.3 m and expect a different plume, because the flame starts about 0.15 m higher in a 2.4 m room.

The first division to understand is gas-phase against solid-phase. A gas-phase device measures a property of the air in a cell, and PyroSim's own documentation is blunt about what that means: the value is taken at the cell centre, regardless of where in the cell you place the device. A solid-phase device measures a property of a surface, and is taken at a cell face; it needs a Normal of Solid so FDS knows which way the surface points.



Why the position inside a cell does not matter



The FDS User's Guide states it directly: FDS uses the device coordinates only to decide which cell the device is in, then reads that cell's centred or face-centred value, and no interpolation is done. So on 10 cm cells a ceiling device typed at 2.35 m and one typed at 2.31 m return identical numbers, because both sit in the cell spanning 2.30 to 2.40 m. Change to 20 cm cells and the same device reads the centre of the 2.20 to 2.40 m cell instead — 2.30 m. The device did not move; the cell did.


A device sitting exactly on a cell boundary is assigned to the cell with the greater coordinate. Thunderhead's tutorial adds a practical warning for solid-phase devices: put the horizontal position inside one cell rather than on a corner, because at a corner FDS will in effect pick one of the four adjoining cells.






The second division is TEMPERATURE against THERMOCOUPLE, and it catches almost everyone. TEMPERATURE is the gas temperature in the cell. THERMOCOUPLE is the temperature of a modelled metal bead sitting in that cell, which absorbs and re-radiates heat and takes time to warm up. The guide's own words are that the thermocouple temperature lags the true gas temperature by an amount set mainly by its bead size. In a short verification run on the historical reference environment, a 20 kW burner in a 1 m box gave 172.6 °C for TEMPERATURE and 84.8 °C for THERMOCOUPLE at the same point at the same instant. Neither is wrong. They are different instruments.



What the bead model actually solves, and its defaults



FDS writes an energy balance on a small sphere: convection from the gas, plus absorbed radiation, minus what the bead re-radiates, divided by the bead's mass and specific heat. In FDS 6.10.1 — the version PyroSim 2026.1 bundles — the defaults are a bead diameter of 0.001 m, an emissivity of 0.85, and the density and specific heat of nickel, 8908 kg/m³ and 0.44 kJ/(kg·K). PyroSim exposes all four as Bead Diameter, Emissivity, Bead Density and Bead Specific Heat.


FDS 6.11.1 changed those last two to Type-K values, 8700 kg/m³ with a specific heat that ramps from 0.4515 kJ/(kg·K) at 20 °C to 0.6010 kJ/(kg·K) at 1200 °C. You are not running 6.11.1, so you get nickel. If you later compare against a paper that used a newer FDS, that is one place the two can differ.


The rule of thumb that follows: if you are emulating a real thermocouple or a real detector, use THERMOCOUPLE. If you want the gas temperature a zone model or a hand correlation would predict, use TEMPERATURE. Do not mix the two inside one channel, and whenever you quote a temperature, say which of the two it came from.






Gases are not separate quantities in FDS 6. Carbon monoxide, carbon dioxide and oxygen are all read with the quantity VOLUME FRACTION plus a SPEC_ID naming the species: 'CARBON MONOXIDE', 'CARBON DIOXIDE', 'OXYGEN'. There is no OXYGEN VOLUME FRACTION quantity in FDS 6, so a menu entry that reads like one is showing you a label, not a keyword. Volume fraction comes out in mol/mol, so a reading of 0.000061 is 61 ppm: ppm is mol/mol multiplied by 1,000,000.



Getting ppm out of PyroSim rather than out of a spreadsheet



FDS can do the multiplication for you. The &DEVC keywords are CONVERSION_FACTOR=1.0E6 with UNITS='ppm', and that is exactly what the reference case uses, so its CO columns are already in ppm with ppm in the units row of the CSV. The research notes for this guide do not record a PyroSim dialog field that writes those two keywords, so on the Windows computer assume you will either multiply mol/mol by 1,000,000 when you read the CSV, or add the keywords to the exported .fds file on Day 7. Whichever you choose, write the choice down: a CO channel that is silently in mol/mol and one that is in ppm differ by six orders of magnitude and both look plausible in a plot.


One more prerequisite, from Day 3: CO and soot only exist in the run if you set CO_YIELD and SOOT_YIELD on the reaction. Both default to zero. With them at zero a CO device does not error: the 1 m test box on the historical reference environment, run once with the yields left out, returned CO exactly 0, optical density 0 and visibility pinned at its 30 m maximum for the whole run.

A smoke layer is not something FDS computes. It is a two-zone construct, and FDS reconstructs it after the fact by integrating temperature along one vertical line — the method of Janssens and Tran. The New Layer Zoning Device entry gives you that line, with three tick boxes: Measure Layer Height, Upper Temperature and Lower Temperature. Both ends of the path must lie in the same mesh.



How to read a layer height that is not moving



FDS integrates the temperature and its reciprocal up the line, solves for an interface height, and reports the upper and lower averages in °C. Solid cells in the column are skipped. The behaviour worth memorising is the fallback: if the computed upper-layer temperature is less than 1 K above the temperature of the lowest cell on the line, FDS returns the full length of the line as the layer height. In a 2.4 m room with the line running floor to ceiling, that is a flat 2.4 m.


So a layer height pinned at exactly the line length is FDS saying "I cannot find a layer here", not "the layer is at the ceiling". On the Mac verification run a corner line of length 1.0 m read 1.0 m for its whole three seconds, for that reason. Layer height is also measured from the lower end of the line, so start the line at z = 0 m if you want heights above the floor.






Last, FED — fractional effective dose. It is a device-only quantity; you cannot make a slice of it. More importantly, the FED device is always a running time integral from the start of the simulation, whatever averaging you ask for. FDS forces that internally. A FED column therefore never falls, and a FED value has no meaning without the time it belongs to. FDS's FED is the asphyxiant model: a carbon monoxide dose multiplied by a carbon dioxide hyperventilation factor, plus a separate oxygen-depletion dose, and no thermal term at all. A reaction with no CO yield leaves only the oxygen term, and heat never enters the number. The FED Activity level is 1 at rest, 2 doing light work, 3 doing heavy work, and the default is 2.

You place a gas-phase device 3 cm from a wall, inside a 20 cm cell. What value does it report?
The value at the centre of that cell. FDS uses the coordinates only to choose the cell and does no interpolation, so anywhere inside the same cell gives the same number. To measure nearer the wall you need a finer mesh, not a nudged device.


At one point and one instant, a TEMPERATURE device reads 172.6 °C and a THERMOCOUPLE device reads 84.8 °C. Which one is broken?
Neither. TEMPERATURE is the gas in the cell; THERMOCOUPLE is a modelled metal bead that has to heat up and that loses heat by radiation, so it lags the gas, and the lag is largest in a fast transient. Report whichever matches the instrument you are comparing against, and say which you used.


The run ends with STOP: FDS completed successfully but one of your devices has no column in CHID_devc.csv. What happened?
Its coordinates fell outside every mesh, so FDS skipped it. The only trace is a console line reading WARNING: DEVC <name> is not within any mesh. Move the device inside the mesh and rerun, and add a check on the log and the column count before you trust a batch.


You change the visibility factor from 3 to 8. What happens to optical density, and what happens to visibility?
Optical density does not change at all — it is the extinction coefficient divided by 2.3 and does not contain the visibility factor. Every visibility reading below the cap is multiplied by 2.67, which is 8 divided by 3. The 30 m maximum stays where it is. This was checked by running the same case twice.


Your FED device reads 0.03 at 900 s and 0.04 at 1195 s. Can a FED column ever fall?
No. FDS forces the FED device to be a running time integral from the start of the simulation, whatever temporal statistic you ask for, so it only ever rises or stays flat. A FED figure is meaningless without the time it was reached at, and the FDS version carries no thermal term — it is the asphyxiant dose only.

PyroSim has been building an FDS input file for four days. Today it hands that file to FDS, and FDS does the physics. Everything you watch from now on is FDS talking; PyroSim starts it, shows you its log, and opens the results afterwards.


There are two launchers, and they are not the same thing. Run FDS starts one FDS process. Thunderhead's own wording is that simulations launched this way can use multiple OpenMP threads, but will not use multiple MPI processes. Run FDS Parallel starts several FDS processes and gives each one its own mesh.


The rule that decides between them is short: one MPI process per mesh, and never more processes than meshes. Ask for more and FDS stops before it starts, with ERROR(112) and the message "The number of MPI processes, 2, exceeds the number of meshes, 1". That message was reproduced in a historical reference run. The second half of the rule is about the machine rather than the model: do not ask for more processes than the desktop has logical processors.


    

  • The room you built has two meshes — the room and the box outside the door — so Run FDS Parallel can use two MPI processes.
    • 

  • A model with one mesh gains nothing from the parallel launcher. Use Run FDS.
    • 

  • Spare cores go to OpenMP threads instead. The FDS User's Guide is blunt about what that buys: "Typically, the use of OpenMP speeds the calculation by at most factor of 2."
    • 



Benchmark mesh and MPI choices on your own computer. Record the case, mesh count, process count and wall-clock time; a historical machine benchmark does not predict another installation.


What MPI and OpenMP actually split


MPI splits the model. Each process owns whole meshes, holds them in its own memory, and swaps boundary data with its neighbours at every time step. That is why the count is tied to meshes and not to cores: a process with no mesh has nothing to do.


OpenMP splits the work inside one process across threads on the same machine. It needs no extra meshes, and it helps much less. PyroSim sets the counts itself — up to four threads for Run FDS and one for Run FDS Parallel — and Thunderhead recommends not changing them.


There is a consequence worth remembering on a shared Windows computer. Thunderhead's own advice is that you may get more total work finished faster by running four simultaneous four-mesh problems on sixteen cores than by throwing everything at one job. On Day 7, when you want many runs rather than one fast run, that is the whole game.




Where the run lands is decided by where you saved the model. PyroSim creates a sub-directory of the current PyroSim file: the documentation's example is that a model saved as C:\pyrosim_files\switchgear.psm puts its results in C:\pyrosim_files\switchgear. The exported .fds file, the geometry files and every output FDS writes all go there. The slice and 3-D smoke files dwarf everything else in that folder, so choose the disk deliberately rather than by accident.


Watch out


Do not save the model inside OneDrive, or on a network drive. The FDS User's Guide states it plainly: "Saving files to a network share or a folder controlled by a cloud service (e.g. OneDrive) can result in simulation failures if a network issue or a file lock during automated backup results in Windows preventing FDS from writing data to a file." The run is writing to those files continuously for hours, so a single lock during a sync can end it.


On a managed office build, Documents is often redirected into OneDrive without saying so. Check the real path before you run, not after. The related symptom is forrtl: severe (47), a write to a read-only file; the documented answers are to run from a folder on a drive physically attached to the machine and outside system folders, and, as a last resort, to add FLUSH_FILE_BUFFERS=F to the &DUMP line.




The window that opens when the run starts is titled FDS Simulation - <your file>.fds. The Fundamentals tutorial calls it "the Run dialog"; the title bar is the software's own name, and where the two disagree the software wins. It carries a log pane that repeats what FDS prints, a Progress bar, Time Elapsed, Time Remaining, a Show results when finished checkbox, and the buttons Kill, Stop, Show Results, Save Log and Open Folder. You can minimise it and carry on using PyroSim, and you can even start another simulation.


Stop and Kill are not two words for the same button. Stop writes a .stop file that signals FDS to stop and also writes a checkpoint file, which often takes a noticeable moment; Resume FDS on the Analysis menu can then continue the run with a restart flag. Kill terminates FDS immediately and you will not be able to resume. Use Stop unless the run is producing nonsense and you want it gone. One trap follows from it: a .stop file left in the folder stops the next run with ERROR(109), telling you to remove that file. Delete it, or resume instead of starting again.


Treat a resumed run as a convenience, not a guarantee


The FDS User's Guide describes restart as "a fragile construct". It works, and it has saved long jobs, but a resumed run is not the same object as a run that went from start to end in one go. For the reference case in this guide, and for anything you will report, prefer one uninterrupted run.

Two: the last time-step block. FDS prints one every 100 steps. It gives the step number, the step size in seconds, the total simulated time in seconds, the pressure iterations, the maximum velocity and pressure errors with the mesh and cell where they occurred, and then, per mesh, the maximum CFL number, the maximum and minimum divergence and the maximum VN number. A healthy last block has the total time equal to your End Time, a step size close to the value the run settled on rather than orders of magnitude below it, and a maximum CFL number below about 1 — FDS adjusts the step to hold CFL between 0.8 and 1. Do not expect the settled step to match the initial time step printed near the top of the file: the reference run starts at 0.184 s, falls to about 0.03 s within the first ten seconds, and ends at 0.015 s, which is normal. A step size that has collapsed by orders of magnitude, next to a CFL number in the hundreds, is the signature of the instability on Day 6.


Three: search the file for "Pressure Zone". In a room with a door to the outside, there should be nothing to find; the 20 cm reference run has no such section. If you do find a Pressure Zone Information heading with a volume in cubic metres and a cell count, FDS has decided part of your model is sealed. FDS assumes any space is perfectly sealed unless you tell it otherwise, so the pressure inside rises, air stops flowing through the door, and an extra pressure column appears in <job>_hrr.csv — and none of this raises an error. The usual causes are a door hole that did not cut all the way through the wall, and an outside mesh with no open boundary vents.

Why FDS cannot do these checks for you
The mistakes FDS can catch are the ones that make the input file unreadable or physically impossible to set up: a misspelt keyword, a burner surface with no reaction, a vent floating in mid-air. Those stop the run before the first time step. Everything else is a modelling choice, and FDS has no opinion about your choices. The FDS User's Guide puts the boundary plainly: physical problems such as fires that do not ignite or flames that do not spread may be related to the mesh resolution or to how the scenario was set up, and you need to investigate the problem yourself before reporting it.


Check one is the cheapest of the three. Your burner surface carries a heat release rate per unit area in kW/m², and the vent or obstruction face it sits on has an area in m². Multiply them and you have the heat release rate you asked for. In the reference case the burner top is 0.2 × 0.2 m, which is 0.04 m², and the surface carries 7500 kW/m². That is 300 kW at full output, and the ramp holds one third of it for the first 600 s, which is the 100 kW stage of the ISO 9705 programme.


Now open CHID_hrr.csv and read the HRR column, which is the heat release rate from gas-phase combustion. It will not be a flat line, because the fire breathes. In the reference run on 20 cm cells it read 109 kW at 60 s, 102 kW at 300 s and 106 kW at 590 s during the 100 kW stage, then 255 kW at 620 s, 323 kW at 900 s and 317 kW at 1195 s after the step to 300 kW. A third either way is the flame moving. A factor of ten is a mistake in the input.

Check three is the outside world. Two references are available for this room without leaving your desk: a hand correlation, and somebody else's measurement. The hand correlation is MQH, published by McCaffrey, Quintiere and Harkleroad and reproduced in NUREG-1805, which estimates the upper-layer temperature rise in a naturally ventilated compartment:


    

  • ΔT = 6.85 · [ Q² / ( (A_v √h_v) · (A_T · h_k) ) ]^(1/3) — ΔT is the upper-layer rise above ambient in K, which is the same size as a rise in °C, and Q is the heat release rate in kW.
    • 

  • A_v is the area of the opening in m² and h_v its height in m, so A_v √h_v is the ventilation factor in m^2.5.
    • 

  • A_T = [2(w·l) + 2(h·w) + 2(h·l)] − A_v — the total area of the walls, floor and ceiling that bound the room, minus the opening, in m².
    • 

  • h_k is the effective heat transfer coefficient of the lining in kW/(m²·K). It has two branches, split by the thermal penetration time t_p = (ρ · c / k) · (δ/2)² in s.
    • 

  • Before the heat has worked through the lining, for t ≤ t_p, use h_k = √(k·ρ·c / t).
    • 

  • Once it has, for t > t_p, use h_k = k/δ.
    • 

  • Units for that last group: k in kW/(m·K), ρ in kg/m³, c in kJ/(kg·K), δ the lining thickness in m, t the time since ignition in s.
    • 



The two branches do not meet smoothly at t = t_p, so always say which one you used and at what time. For this room the numbers are fixed by the standard: the door is 0.8 × 2.0 m, so A_v = 1.60 m², h_v = 2.0 m and A_v √h_v = 2.263 m^2.5. The room is 3.6 × 2.4 × 2.4 m, so A_T = 46.08 − 1.60 = 44.48 m². The lining decides h_k, and the standard does not specify one, which is why the guide's case states its own: aerated concrete, k 0.26 W/m·K, ρ 500 kg/m³, c 0.96 kJ/kg·K, 0.1 m thick, from NUREG-1805 Table 2-3. With those values t_p is about 4600 s, so through the whole 1200 s programme the lining is still soaking up heat and the first branch applies.

Watch out
MQH was fitted to about 100 experimental fires with the fire away from the walls, and NUREG-1805 states that the correlation is not valid with the coefficient 6.85 if the fire is flush with a wall or in a corner. Only the last line of the console or of CHID.out reading STOP: FDS completed successfully. FDS returns 0 after set-up errors and after a numerical instability, so any script that checks the exit code alone will report broken runs as successes.


Your burner surface has 7500 kW/m² on a 0.2 × 0.2 m top, and the HRR column sits at 102 kW during the first stage. Is that a problem?
No. The arithmetic gives 7500 × 0.04 = 300 kW at full output and 100 kW on the one-third stage, and the column varies as the flame moves. Your .out file lists a Pressure Zone Information block with a volume close to your room's volume. What has happened, and where else does it show?

Why decimation and not a 5-second average
A mean over five seconds is a low-pass filter. It removes the fast part of the signal, and the fast part is the forecast: a network trained to see temperature climbing at so many degrees per second cannot see it in a series that has been smoothed first.

Scenarios enumerate, and that is honest work for a handful of variants


PyroSim has a feature for variations of one model, called Scenarios, and it is worth knowing exactly what it stores. Thunderhead's documentation is direct about the limit: scenarios only explicitly track the enabling and disabling of objects, and to modify an object parameter in a scenario, the object must be duplicated, the parameter in the duplicate must be modified, and the original object must be disabled in the scenario.


Their own worked example shows the cost. To run the same room with a burner at 1000 kW/m² and again at 2000 kW/m² on a 1.0 m² vent, you copy the vent, create a second surface from the fire template, set its heat release rate, assign it to the copy, then disable the original in one scenario and the copy in the other. That is four objects to keep consistent for one changed number. Change four numbers at once, as today's batch does, and the duplicates multiply.


What Scenarios do well is the running. Export Scenarios writes each scenario's .fds file into its own subfolder beside the saved model, and writes a BAT file that can be double-clicked in Windows Explorer to run them all in sequence. The documentation also warns why you should use it rather than running scenarios one at a time from Run FDS: running individually overwrites the same results file every time. For five or ten hand-made variants, this route is the right one, and it needs no scripting at all.


For hundreds of runs, the file itself becomes the template


The other route treats the exported .fds file as text. You export one file from the model you have spent six days building, replace the values that vary with placeholders, and let a script fill them in. PyroSim stays the authoring tool; the script only substitutes numbers into a file PyroSim wrote.


The risk is that a generated file can be wrong in ways FDS does not object to, and Day 4 and Day 6 have shown you several. An obstruction too small for the mesh is rejected, and the guide is explicit that if at least two of the three obstruction dimensions are less than half of the corresponding cell dimensions, the obstruction is ignored. A vent must be a plane on a solid. Anything reaching past the mesh is cut off at the boundary. A device outside every mesh loses its column from the CSV with a console warning and nothing else. So the generator validates each variant before it writes a file, and refuses the ones that break those rules.

What the two scripts do, and what they refuse


make_scenarios.py varies four things a real room fire varies: the peak heat release rate, chosen from 100, 200, 300, 500, 750 and 1000 kW; the growth class, one of the four standard t-squared curves, slow, medium, fast and ultra-fast, which reach about 1054 kW in 600, 300, 150 and 75 s; the burner's position anywhere on the floor grid; and the door width from 0.4 m to 1.2 m. A bigger fire is drawn as a wider burner rather than a hotter one, aiming at roughly 1000 kW/m², and the growth class plus the peak become a negative TAU_Q — for that first variant, −160.0 s.


It refuses more than it accepts, which is the point. A variant is rejected if the burner corner or either door edge is off the cell grid, if the burner reaches outside the room or through the front wall, if the peak falls outside 50 to 2000 kW, or if the burner would sit on top of the floor heat-flux gauge at 1.85, 1.25 m or the layer-height line at 3.25, 2.15 m. The last of those is the one a person would miss: the file would run to completion and quietly return a floor flux measured through the burner.


fds_to_dataset.py reads units and device names from the two FDS header rows. It keeps the reading nearest each five-second mark and emits time_s, zone, temperature_c, optical_density, co_ppm, visibility_m and fed. CO is converted from ppm, mol/mol or %; unknown units, gaps and non-finite values are rejected.

The reaction has no yields. FDS defaults CO_YIELD and SOOT_YIELD to zero, and the library's FDS6 fuel entries, propane included, set only the fuel. Visibility then sits at its 30 m cap and part of the exposure dose never accumulates.
Open Model › Edit Reactions, go to the Byproducts tab and set both. The reference case uses 0.024 soot and 0.005 CO for propane, the values the FDS Validation Guide adopts from Tewarson's measurements.




A wall or ceiling stays exactly at room temperaturesilent
Its surface is still INERT, the default, which holds the surface at the ambient temperature.
Give it a layered surface with real materials. Do not reach for ADIABATIC instead: the FDS guide says it is for testing only.




The run stops part wayERROR(374): Numerical Instability - FDS stopped
The time step collapsed below one ten-thousandth of its initial value. Documented causes include a sudden large change in heat release, cells with an aspect ratio worse than 2:1, a resolution jump at a mesh interface, high-speed flow through a small opening, and a fire too large for the room's ventilation.
Read the last time-step block in CHID.out for the mesh where the CFL number or divergence explodes, then open the final Plot3D file FDS writes in Smokeview and look for the spurious velocities. Ramp the fire instead of stepping it, and keep the domain open beyond the door.




FDS stops while reading the fileERROR(101): Problem with SURF number 2, line number 49
A misspelt or invalid keyword, a missing closing slash, a wrong quote, or a non-ASCII character. FDS names the record type and the line.
Go to that line. Note that an unused RAMP with a typo is never read and never complains, so the fault can be in a line you thought was inactive.




ERROR(314): SURF BURNER Must have a REAC line when using HRRPUA or MLRPUA.
A burner surface with no reaction defined.
Model › Edit Reactions › Add From Library, then set the yields.




ERROR(819): VENT null is OPEN, MIRROR OR PERIODIC and must be on an exterior boundary.
An OPEN vent was drawn inside the domain, often on an interior wall where a door was meant.
OPEN belongs only on the outside faces of a mesh. Model a door as a hole through the wall.




ERROR(820): VENT 1 has no solid backing or an orientation index (IOR) is needed.
The vent is floating in air. A vent must sit on a solid face or a mesh boundary.
Put it on the face of an obstruction, or give it an orientation. The 6.11 wording differs: VENT <id> is not attached to any solid surface.




ERROR(431): MESH 2 is out of alignment with MESH 1
Abutting meshes whose cells do not match in cross-section or in an integer ratio.
Make the shared face line up. To check without running, set the end time to zero — the alignment error still prints, and the run ends with STOP: Set-up only.




ERROR(112): The number of MPI processes, 2, exceeds the number of meshes, 1
A parallel run asks for more processes than there are meshes. One mesh takes one process.
Split the model into more meshes, or run fewer processes. Keep the fire inside one mesh.




ERROR(108): No periods allowed in CHID
The job name contains a full stop. Spaces are out too, and the same rule applies to the folder name.
Use underscores: room_v1, not room.v1.




ERROR(109): Remove the file, case.stop, from the current directory
A previous run was stopped and left its .stop file behind.
Delete it, or resume the run with Analysis › Resume FDS, which restarts from the checkpoint.




The run ends immediately with nothing in it
A new PyroSim model has a simulation end time of 0.001 s, which must be changed before anything happens. FDS's own default is 1 s.
Analysis › Simulation Parameters › Time, set the end time.




FDS runs far slower than expected on Windows
Windows Defender scanning the solver. The installer adds exclusions for the bundled FDS, but not for an FDS you point at yourself.
Add file and process exclusions for fds.exe and fds_openmp.exe in Windows Security.




The licensing dialog opens at start-up
PyroSim cannot find a licence.
Help › License. A node-locked licence takes a 22-character activation key, or a licence file generated from the host ID shown in the dialog. A floating licence takes the server name and port 52100.




Parallel runs ask for a password, repeatedly
MPI on Windows needs a password-protected account.
Set an account password, then in the install's fds\mpi folder run mpiexec -remove, mpiexec -register and mpiexec -validate.




A batch reports success for runs that failed
FDS returns exit status 0 after set-up errors and after a numerical instability. The status tells you nothing.
Search each log for the exact line STOP: FDS completed successfully, and flag any ERROR(, any device warning and any unexpected pressure zone.




Every variant overwrites the last one's results
Output files are named from the CHID, so two runs with the same CHID share files.
One CHID per variant, and one folder per variant. In PyroSim use File › Export › Export Scenarios rather than running scenarios one at a time.




The disk fills during a batch
Slice, boundary and 3D smoke files are written a thousand times per run by default, whatever the run length.
Set the output intervals explicitly on the Output tab, keep only the slices you need, and turn 3D smoke off for data runs.












Glossary


The words this field uses, and the ones that stay in English


Tool names, FDS keywords, file names and the vocabulary a Hong Kong fire engineer says in English stay in English in both versions of this page: PyroSim, FDS, Smokeview, HRR, mesh, SURF, DEVC, SLCF, CSV. The Chinese terms below follow the terminology used throughout this guide.






Heat release rateHRR · 放熱率
How much power the fire is putting out, in kilowatts. In this guide it is prescribed, not predicted: you tell FDS what the burner does.


HRRPUA單位面積放熱率
Heat release rate per unit area, in kW/m². Multiply by the burner's area to get the fire's power. The commonest beginner error is typing kilowatts here.


Mesh, cell size網格 · 格距
The grid of boxes FDS solves on. Everything smaller than a cell is invisible to the simulation, so the cell size sets what the answer can possibly show.


Smoke layer, layer height煙層 · 煙層高度
The hot smoky region under the ceiling and the height of its lower edge. FDS does not compute a layer directly; it estimates one from a temperature profile along a line.


Visibility能見度
How far a person could see an exit sign through the smoke, in metres. FDS caps it at 30 m and derives it from the smoke's optical density.


Optical density光學密度
How much light smoke absorbs per metre. The exporter retains optical density directly rather than converting it to a risk label.


Obscuration遮光度
The same idea as a percentage of light lost per metre. Smoke detectors are rated in these units.






Flashoverflashover · 閃燃
The moment a room fire becomes a fire of the whole room. ISO 9705 defines it as 1000 kW; in practice people also use a 600 °C upper layer or 20 kW/m² at the floor.


Tenability可維生性
Whether a person could still survive and escape: enough visibility, low enough heat, a low enough dose of gas.


FED有效劑量分數
Fractional effective dose. A running total of the gas exposure a person at that point would have taken, where 1.0 means incapacitation.


Soot yield, CO yield煙塵產率 · 一氧化碳產率
The fraction of burnt fuel mass that becomes smoke particles or carbon monoxide. Both default to zero in FDS, which is why smoke and CO can stay flat all run.


Device量測裝置
A virtual sensor in the model. A gas-phase device reads the centre of the cell it sits in, whatever its exact coordinates.


Scenario情景
A variation of one model. PyroSim's Scenarios feature only turns objects on and off, which is why Day 7 uses a text template instead.


Simulation case個案
One run: one input file, one CHID, one folder of results. A dataset is many cases.
